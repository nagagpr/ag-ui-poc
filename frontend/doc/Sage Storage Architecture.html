Where Sage's data should actually live

Right now every write — results, recordings, reports, AI-driver artifacts — lands on the ECS task's local disk. When the task is replaced, it's gone. Here's the target architecture, split by data type, with the cost reasoning behind each choice.

File & binary artifacts Amazon S3

Recorded tests, execution reports, explorer and Figma results, AI-driver screenshots and videos — all of it is the same pattern: write a file, read it back later. That's exactly what S3 is built for, and it's roughly 13× cheaper per GB than the alternative below for the identical workload.

Why S3, not a mounted filesystem

It decouples storage from the ECS task entirely — no volume-mount complexity, no risk of losing data when a task is replaced. It also supports presigned URLs, so the UI can fetch a screenshot or video directly instead of proxying it through the app, and it's a one-line addition to CloudFront if reports ever need to be served publicly.

Set these as S3 Lifecycle rules once, and old test runs and audit artifacts age themselves down in cost automatically — no app change required after the initial migration.

Structured & relational data RDS for PostgreSQL

Audits, the Quality Graph, reconciliation data, lifecycle/test-repository metadata, and Ask SAGE sessions all imply relationships, joins, and a queryable audit trail. That calls for a relational engine, not raw files or a pure key-value store.

Why not Aurora Serverless by default

Aurora Serverless v2 scales up cleanly but has a real floor — about $43/month at its 0.5 ACU minimum, billed whether or not it's used. It no longer scales to near-zero the way Serverless v1 did. At this scale, a small single-AZ RDS instance is simply cheaper. Reach for Aurora Serverless v2 only if traffic is genuinely unpredictable and spiky.

Why not EFS Interim only

EFS is the zero-code-change option: mount it, the app keeps writing to the same filesystem paths, done in an afternoon. That's the entire case for it — it is not the cost-optimized end state.

~13× the per-GB cost of S3 for the identical read/write pattern, and none of S3's lifecycle-based cost controls for aging out old artifacts.

Suggested path

  1. Now — unblock ECS

    Mount EFS as an interim fix

    If persistence needs to work immediately with no app rewrite, mount EFS into the ECS task so nothing is lost on task replacement while the target-state migration is planned.

  2. Next — target state

    Migrate to S3 + RDS Postgres

    Move file writes to the S3 SDK (@aws-sdk/client-s3 in Node) and move relational/audit data to RDS Postgres. This is the industry-standard end state, and meaningfully cheaper at any real volume.
