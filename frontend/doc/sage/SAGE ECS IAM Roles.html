Step 2 — VPC: private subnets and outbound access

Performed byIT network team

Use an approved company VPC, not the default VPC. sage5.0 tasks and its load balancer run in 2 private subnets in 2 different Availability Zones, with no public IP.

  1. Console: VPC → Subnets → filter by <VPC_ID> → choose two private subnets in different AZs (for example us-east-1a and us-east-1b). Each needs at least ~20 free IP addresses.
  2. Open each subnet's route table. It must have a route 0.0.0.0/0 → nat-… (NAT Gateway) or to the company's approved egress (Transit Gateway / firewall). It must not route to an internet gateway (igw-…).
  3. Outbound internet access is required. sage5.0 calls Jira (tbscg-team.atlassian.net), Azure OpenAI (*.services.ai.azure.com) and Figma (api.figma.com) at runtime. If egress goes through a firewall or proxy, allow these hosts on HTTPS 443.
  4. Give the subnet IDs and the VPC ID to the IT / Cloud team for the next steps.
Only if there is no NAT Gateway yet

Create one in a public subnet of the same VPC (VPC → NAT gateways → Create, connectivity type Public, allocate an Elastic IP). Then add 0.0.0.0/0 → nat-… to the private subnets' route table. A NAT Gateway is billed hourly plus per GB of traffic.

Step 3 — VPC endpoints (recommended)

Performed byIT network team

Endpoints keep ECR, CloudWatch Logs and S3 traffic inside AWS, so it doesn't go through the NAT Gateway (cheaper and more private). Skip them if the company already provides shared endpoints in this VPC.

  1. Create security group sage5-0-vpce-sg in <VPC_ID>. Inbound: HTTPS 443 from sage5-0-ecs-sg (created in Step 4, so add this rule after Step 4). Outbound: default.
  2. Console: VPC → Endpoints → Create endpoint → AWS services → create interface endpoints com.amazonaws.us-east-1.ecr.api, com.amazonaws.us-east-1.ecr.dkr and com.amazonaws.us-east-1.logs. Use the two private subnets and sage5-0-vpce-sg, with Enable private DNS name ticked.
  3. Create a gateway endpoint com.amazonaws.us-east-1.s3 attached to the private subnets' route table(s). ECR stores image layers in S3, and the app writes to S3.

Step 5 — Amazon ECR repository

Performed byIT / Cloud team

Console: ECR → Private registry → Repositories → Create repository → name sage5.0 → Image scan: Scan on push → Encryption: AES-256 → Create. Then Lifecycle policy → keep the last 30 images.

Step 6 — Amazon S3 bucket

Performed byIT / Cloud team

Console: S3 → Create bucket → name <S3_BUCKET>, region us-east-1 → Object Ownership: ACLs disabled → Block all public access: on → Default encryption: SSE-S3 → Create. Then Permissions → Bucket policy, and paste the policy below. No folders are needed; sage/ appears when the app writes its first file.

Step 7 — CloudWatch log group

Performed byIT / Cloud team

Console: CloudWatch → Log groups → Create log group → name /ecs/sage5.0 → retention per company policy (example 30 days).

Step 8 — Target group

Performed byIT / Cloud team

Console: EC2 → Target Groups → Create target group → target type IP addresses (required for Fargate) → name sage5-0-tg → protocol HTTP, port 5000 → VPC <VPC_ID> → health check path /api/health, success code 200 → Next → don't register targets (ECS does it) → Create.

Step 9 — Application Load Balancer

Performed byIT / Cloud team

Console: EC2 → Load Balancers → Create → Application Load Balancer → name sage5-0-alb → scheme Internal → IPv4 → VPC <VPC_ID> → the 2 private subnets → security group sage5-0-alb-sg (remove default) → listener HTTP 80 → forward to sage5-0-tg → Create. Note the DNS name; other services use it to call sage5.0.

Only if users' browsers must reach sage5.0 directly

Use scheme internet-facing in two public subnets. Add an HTTPS 443 listener with the company ACM certificate (and an HTTP 80 → HTTPS 301 redirect), and allow 443 inbound from the approved CIDRs on sage5-0-alb-sg. Put AWS WAF in front if company policy requires it. The ECS tasks still stay in the private subnets.

Step 10 — ECS cluster

Performed byIT / Cloud team

Console: ECS → Clusters → Create cluster → name <ECS_CLUSTER> → Infrastructure: AWS Fargate (serverless) only → Monitoring: Container Insights (optional) → Create. Skip this step if the cluster already exists.

Step 11 — ECS task definition (first revision)

Performed byIT / Cloud team with Application team

The task definition says which image to run, with which roles, port, CPU/memory and log group. IT registers revision 1. After that, the pipeline registers a new revision on every deployment, changing only the image tag and the environment values.

Save as sage5-0-taskdef.json (replace <ACCOUNT_ID>, <S3_BUCKET>):

The image doesn't exist yet. That's fine, because the service is created with 0 tasks in Step 12, and the first pipeline run pushes the image.

Step 12 — ECS service

Performed byIT / Cloud team

Console: ECS → Clusters → <ECS_CLUSTER> → Services → Create:

  • Compute options: Launch type → FARGATE, platform version LATEST.
  • Application type Service, family sage5-0, latest revision, service name sage5-0, desired tasks 0 (raised to 1 in Step 14).
  • Deployment: rolling update, min 100% / max 200%, deployment circuit breaker with rollback: on.
  • Networking: VPC <VPC_ID>, the 2 private subnets, security group sage5-0-ecs-sg only, Public IP: off.
  • Load balancing: Application Load Balancer → existing sage5-0-alb → container sage5-0 5000:5000 → existing listener 80 → existing target group sage5-0-tg. Health check grace period 120 seconds.

Hand over to the application team: account ID, cluster name, the three role ARNs, the ALB DNS name, and confirmation that service sage5-0 exists.

13.3 Workflow `.github/workflows/deploy-sage5.yml`

Add any other app variables (Recorder, Playwright, Azure deployment names, timeouts) to the environment-variables list in the same way, and keep the existing build arguments (for example JFrog) in the build step if the Dockerfile needs them.

Secrets in environment variables

Values passed this way are stored in the task definition and are visible to anyone with ecs:DescribeTaskDefinition. That matches today's setup, but it is a known risk. The better follow-up is to store them in AWS Secrets Manager and reference them as container secrets. That needs secretsmanager:GetSecretValue on the execution role.

Step 14 — First deployment and verification

Performed byApplication team (IT observes)

  1. GitHub → Actions → Deploy sage5.0 (ECS) → Run workflow, then approve the production gate.
  2. Check that each step passed: credentials (OIDC trust OK) → ECR login → image push → task definition rendered → deploy.
  3. Start the first task (IT, once): aws ecs update-service --cluster $CLUSTER --service sage5-0 --desired-count 1. Later deployments keep this count.
  4. ECS → cluster → sage5-0 → Deployments / Tasks: one task RUNNING, no CannotPullContainerError or ResourceInitializationError events.
  5. EC2 → Target Groups → sage5-0-tg → Targets: the task IP is healthy.
  6. CloudWatch → Log groups → /ecs/sage5.0: start-up log lines, and the server listening on port 5000.
  7. From inside the VPC (for example a caller service or an SSM-connected host): curl -s http://<ALB_DNS_NAME>/api/health returns HTTP 200.
  8. Run one app flow that saves a file, then aws s3 ls s3://$BUCKET/sage/ --recursive shows the new object.
  9. Re-run the workflow once more: the new task becomes healthy and the old one is drained, with no downtime.

Final checklist

  • OIDC provider and ECS service-linked role exist
  • 2 private subnets in 2 AZs with NAT / approved egress; Jira, Azure OpenAI and Figma reachable
  • VPC endpoints for ecr.api, ecr.dkr, logs and S3 (or company shared endpoints)
  • Security groups sage5-0-alb-sg, sage5-0-ecs-sg, sage5-0-vpce-sg with only the rules in Step 4
  • ECR repository sage5.0 with scan on push and lifecycle policy
  • S3 bucket: public access blocked, SSE-S3, deny-non-TLS policy
  • Log group /ecs/sage5.0 with retention
  • Target group sage5-0-tg (ip, 5000, /api/health) and internal ALB sage5-0-alb with listener 80
  • ECS cluster (Fargate), task definition sage5-0 with both role ARNs, service sage5-0 in private subnets, no public IP, circuit breaker on
  • GitHub production environment with reviewers; secrets and variables set; ECS_INFRASTRUCTURE_ROLE_ARN removed
  • First deployment healthy; logs visible; S3 write works; second deployment has no downtime
  • Jira, Azure OpenAI and Figma credentials rotated (they were exposed in a text file)
