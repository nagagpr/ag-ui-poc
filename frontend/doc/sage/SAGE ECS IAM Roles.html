SAGE 5.0 on Amazon ECS: Console Setup Guide

AWS Console step-by-step setup of everything after the IAM roles: network, security groups, ECR, S3, CloudWatch, load balancer, ECS and GitHub Actions for sage5.0 (classic ECS on Fargate, no Express Mode, no default VPC)

Version
Version 1.0 · 18 October 2026
Audience
IT network team, IT / Cloud team, SAGE application team

0. Before you start

  • Sign in to the AWS Console in the target account and set the region (top right) to US East (N. Virginia) us-east-1 for every step.
  • The three IAM roles already exist: sage-github-actions-deploy-role, sage-ecs-task-execution-role, sage-storage-task-role.
  • AWS occasionally renames buttons. If a label differs slightly, use the closest match; the field values stay the same.

Step 1 — IAM: GitHub OIDC identity provider

Performed byIT / Cloud team

Needed once per account, so GitHub Actions can assume sage-github-actions-deploy-role without AWS keys.

  1. Open IAM → Identity providers. If token.actions.githubusercontent.com is already listed, skip this step.
  2. Click Add provider.
  3. Provider type: OpenID Connect.
  4. Provider URL: https://token.actions.githubusercontent.com
  5. Audience: sts.amazonaws.com
  6. Click Add provider.

The ECS service-linked role (AWSServiceRoleForECS) is created automatically when you create the ECS cluster in Step 10. Nothing to do now.

Step 2 — VPC: check private subnets and outbound access

Performed byIT network team

Use an approved company VPC, not the default VPC. sage5.0 runs in 2 private subnets in 2 different Availability Zones, with no public IP.

  1. Open VPC → Subnets. In the filter, choose VPC <VPC_ID>.
  2. Pick two private subnets in different Availability Zones (column *Availability Zone*, e.g. us-east-1a and us-east-1b), each with at least ~20 free IPs (column *Available IPv4 addresses*). Note both subnet IDs.
  3. Select each subnet → Route table tab. There must be a route Destination 0.0.0.0/0 → Target nat-… (NAT Gateway) or the company's approved egress (Transit Gateway / firewall). It must not be igw-… (that would make it a public subnet).
  4. Confirm with the network/firewall team that HTTPS 443 is allowed outbound to Jira (tbscg-team.atlassian.net), Azure OpenAI (*.services.ai.azure.com) and Figma (api.figma.com). sage5.0 calls these at runtime.
  5. Send the VPC ID and both subnet IDs to the IT / Cloud team.
Only if there is no NAT Gateway

VPC → NAT gateways → Create NAT gateway: subnet = a public subnet of the same VPC, connectivity type Public, Allocate Elastic IP → Create. Then VPC → Route tables → the private subnets' route table → Routes → Edit routes → Add route: 0.0.0.0/0 → NAT Gateway → Save. A NAT Gateway is billed hourly plus per GB of traffic.

Step 3 — EC2: security groups

Performed byIT / Cloud team

Create all three groups empty first (rules refer to each other), then add the rules.

3.1 Create the three groups

Open EC2 → Network & Security → Security Groups → Create security group. Create each one with VPC <VPC_ID>, no inbound rules, and leave the default outbound rule for now:

Security group nameDescription
sage5-0-alb-sgsage5.0 internal load balancer
sage5-0-ecs-sgsage5.0 ECS tasks
sage5-0-vpce-sgVPC endpoints for sage5.0

3.2 Add the rules

Select a group → Inbound rules → Edit inbound rules → Add rule / Outbound rules → Edit outbound rules. For *Source/Destination: Custom*, start typing sg- or the group name and pick it from the list.

Security groupInbound rulesOutbound rules (delete the default "All traffic" rule)
sage5-0-alb-sgCustom TCP · port 80 · source <CALLER_SG_ID> (or <CORPORATE_CIDR>). Never 0.0.0.0/0Custom TCP · port 5000 · destination sage5-0-ecs-sg
sage5-0-ecs-sgCustom TCP · port 5000 · source sage5-0-alb-sgHTTPS · port 443 · destination 0.0.0.0/0 (ECR, logs, S3, Jira, Azure OpenAI, Figma)
sage5-0-vpce-sgHTTPS · port 443 · source sage5-0-ecs-sgLeave the default

Click Save rules after each edit.

Step 4 — VPC: endpoints (recommended)

Performed byIT network team

Endpoints keep ECR, CloudWatch Logs and S3 traffic inside AWS (cheaper than NAT, and private). Skip this step if the company already provides shared endpoints in this VPC.

4.1 Three interface endpoints (repeat for each)

  1. Open VPC → Endpoints → Create endpoint.
  2. Name tag: sage5-0-ecr-api (then sage5-0-ecr-dkr, sage5-0-logs).
  3. Type: AWS services. In *Services*, search and select com.amazonaws.us-east-1.ecr.api (then …ecr.dkr, then …logs), type Interface.
  4. VPC: <VPC_ID>. Expand Additional settings → tick Enable DNS name.
  5. Subnets: tick both AZs and choose the 2 private subnets.
  6. Security groups: untick default, tick sage5-0-vpce-sg.
  7. Policy: Full access → Create endpoint.

4.2 One gateway endpoint for S3

  1. VPC → Endpoints → Create endpoint, name sage5-0-s3.
  2. Type AWS services → search s3 → select com.amazonaws.us-east-1.s3 with type Gateway.
  3. VPC <VPC_ID> → Route tables: tick the route table(s) used by the 2 private subnets.
  4. Policy: Full access → Create endpoint.

Step 5 — ECR: repository

Performed byIT / Cloud team

  1. Open Amazon ECR → Private registry → Repositories → Create repository.
  2. Repository name: sage5.0.
  3. Image tag mutability: Immutable (every build is tagged with its Git commit, so tags never need to change).
  4. Encryption: AES-256 → Create.
  5. Scan on push: if the create page shows *Scan on push*, turn it on. Otherwise go to Private registry → Features & Settings → Scanning → Edit, choose Basic scanning, add a *Scan on push* filter sage5.0 → Save.
  6. Open repository sage5.0 → Lifecycle policy → Create rule: priority 1, description Keep last 30 images, image status Any, match criteria Image count more than 30 → Save.

Step 6 — S3: bucket

Performed byIT / Cloud team

  1. Open S3 → Buckets → Create bucket.
  2. Bucket type: General purpose. Bucket name: <S3_BUCKET> (region shows US East (N. Virginia)).
  3. Object Ownership: ACLs disabled (recommended).
  4. Block Public Access settings: Block *all* public access — ticked.
  5. Bucket Versioning: Disable (choose *Enable* only if audit files must be protected from overwrite — confirm with compliance).
  6. Default encryption: Server-side encryption with Amazon S3 managed keys (SSE-S3), Bucket Key Enable → Create bucket.
  7. Open the bucket → Permissions → Bucket policy → Edit → paste the policy below (replace <S3_BUCKET> twice) → Save changes.

No folders are needed. sage/ appears when the application writes its first file.

Step 7 — CloudWatch: log group

Performed byIT / Cloud team

  1. Open CloudWatch → Logs → Log groups → Create log group.
  2. Log group name: /ecs/sage5.0
  3. Retention setting: per company policy (example 1 month). Log class: Standard → Create.

Step 8 — EC2: target group

Performed byIT / Cloud team

  1. Open EC2 → Load Balancing → Target Groups → Create target group.
  2. Target type: IP addresses (required for Fargate).
  3. Target group name: sage5-0-tg. Protocol HTTP, port 5000. IP address type IPv4. VPC <VPC_ID>. Protocol version HTTP1.
  4. Health checks: protocol HTTP, path /api/health.
  5. Expand Advanced health check settings: healthy threshold 2, unhealthy threshold 3, timeout 5, interval 30, success codes 200 → Next.
  6. Register targets page: don't add any IPs (ECS registers the tasks itself) → Create target group.
  7. Open sage5-0-tg → Attributes → Edit → Deregistration delay 30 seconds → Save changes (faster deployments).

Step 9 — EC2: Application Load Balancer

Performed byIT / Cloud team

  1. Open EC2 → Load Balancing → Load Balancers → Create load balancer → Application Load Balancer → Create.
  2. Load balancer name: sage5-0-alb. Scheme: Internal. IP address type: IPv4.
  3. Network mapping: VPC <VPC_ID> → tick both AZs → select the 2 private subnets.
  4. Security groups: remove default, select sage5-0-alb-sg.
  5. Listeners and routing: protocol HTTP, port 80, default action Forward to sage5-0-tg.
  6. Create load balancer. Wait until state is Active, then copy the DNS name from the details (callers use it to reach sage5.0).
Only if users' browsers must reach sage5.0 directly

Choose scheme Internet-facing and two public subnets instead. Add listener HTTPS 443 with the company certificate from ACM, and change the HTTP 80 listener to Redirect to HTTPS 443. On sage5-0-alb-sg, allow 443 from the approved CIDRs. Attach AWS WAF if company policy requires it. The ECS tasks still stay in the private subnets.

Step 10 — ECS: cluster

Performed byIT / Cloud team

  1. Open Amazon Elastic Container Service → Clusters → Create cluster. Skip this step if <ECS_CLUSTER> already exists.
  2. Cluster name: <ECS_CLUSTER>.
  3. Infrastructure: AWS Fargate (serverless) only. Leave Amazon EC2 instances unticked.
  4. Monitoring: Container Insights (optional, small extra cost) → Create.
  5. Check: IAM → Roles now lists AWSServiceRoleForECS.

Step 11 — ECS: task definition (first revision)

Performed byIT / Cloud team with Application team

The task definition tells ECS which image to run, with which roles, port, CPU/memory and log group. IT creates revision 1. After that, the pipeline creates a new revision on every deployment, changing only the image and environment values.

Recommended (fewer mistakes): create it from JSON.

  1. Open ECS → Task definitions → Create new task definition → Create new task definition with JSON.
  2. Delete the sample, paste the JSON below, replace <ACCOUNT_ID> (3 places) and <S3_BUCKET> → Create.

Or with the form (Create new task definition):

Step 13 — GitHub: environment, secrets, variables, workflow

Performed byApplication team

All in the GitHub web UI for repository sanumolu-rnt-c/sage5.0.

  1. Settings → Environments → New environment → name production → Configure environment.
  2. Tick Required reviewers and add the approvers.
  3. Deployment branches and tags: Selected branches → add master → Save protection rules.

Delete ECS_INFRASTRUCTURE_ROLE_ARN (Express Mode only). ECS_EXECUTION_ROLE_ARN and ECS_TASK_ROLE_ARN are no longer used: the roles come from the task definition.

13.3 Workflow file

In the repository: Add file → Create new file → name .github/workflows/deploy-sage5.yml → paste → Commit changes (to a branch + pull request if master is protected).

Add any other app variables (Recorder, Playwright, Azure deployment names, timeouts) to environment-variables the same way. Keep any build arguments (for example JFrog) the Dockerfile needs in the build step.

Secrets in environment variables

Values passed this way are stored in the task definition and can be read by anyone with access to it in the ECS console. That matches today's setup. The safer follow-up is AWS Secrets Manager with container secrets (needs secretsmanager:GetSecretValue on the execution role).

Step 14 — First deployment and verification

Performed byApplication team (IT observes)

  1. GitHub → Actions → Deploy sage5.0 (ECS) → Run workflow → Run workflow. Approve the production review when asked.
  2. Open the run: every step must be green. *Configure AWS credentials* proves the OIDC trust; *Deploy to ECS service* proves the ECS and PassRole permissions.
  3. Start the first task (IT, once): ECS → Clusters → <ECS_CLUSTER> → Services → sage5-0 → Update service → Desired tasks 1 → Update. Later deployments keep this count.
  4. Services → sage5-0 → Tasks tab: one task Running. The Deployments and Events tabs show no CannotPullContainerError or ResourceInitializationError.
  5. EC2 → Target Groups → sage5-0-tg → Targets tab: the task IP shows healthy.
  6. CloudWatch → Log groups → /ecs/sage5.0 → latest log stream: start-up lines, with the server listening on port 5000.
  7. Run one app flow that saves a file, then S3 → <S3_BUCKET> → sage/ shows the new object.
  8. Run the workflow once more. The new task becomes healthy and the old one drains, with no downtime.

Final checklist

  • GitHub OIDC identity provider exists; AWSServiceRoleForECS exists
  • 2 private subnets in 2 AZs with NAT / approved egress; Jira, Azure OpenAI and Figma allowed
  • Security groups sage5-0-alb-sg, sage5-0-ecs-sg, sage5-0-vpce-sg with only the rules in Step 3
  • VPC endpoints for ecr.api, ecr.dkr, logs and S3 (or company shared endpoints)
  • ECR repository sage5.0: immutable tags, scan on push, lifecycle policy
  • S3 bucket: all public access blocked, SSE-S3, deny-non-HTTPS policy
  • Log group /ecs/sage5.0 with retention
  • Target group sage5-0-tg (IP, 5000, /api/health) and internal ALB sage5-0-alb listening on 80
  • ECS cluster (Fargate); task definition sage5-0 with both roles and log group /ecs/sage5.0
  • ECS service sage5-0: private subnets, public IP off, circuit breaker with rollback, attached to sage5-0-tg
  • GitHub production environment with reviewers; secrets and variables set; ECS_INFRASTRUCTURE_ROLE_ARN deleted
  • First deployment healthy; logs visible; S3 write works; second deployment has no downtime
  • Jira, Azure OpenAI and Figma credentials rotated (they were exposed in a text file)
