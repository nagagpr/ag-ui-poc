## SEC-1 — Generated Playwright spec can execute attacker-controlled code (Critical)

```
#codebase
Branch: fix/sec-1-generated-spec-injection

PROBLEM (from security audit)
POST /api/testcases/generate-spec (testcases.route.ts ~89) accepts test cases from the request.
The spec builder (testcase.tool.ts ~202) inserts classification.themeName, category, repository
IDs, steps and expected text into the generated TypeScript source (comments and code) without
consistently escaping line breaks or quotes. The file is written to the Playwright test directory
(testcase.tool.ts ~230), added to the script catalog (testcases.route.ts ~131), and the catalog
has a route that executes the spec (script-catalog.route.ts ~51). A newline in any field can end a
comment and inject code before test.fixme(...), which then runs on the server.

FIX
1. Never interpolate user text into executable source. Preferred design: the generated spec
   contains only fixed code; all test data (titles, steps, expected results, category, theme,
   repository ids) is written to a sibling JSON data file and loaded with JSON.parse at runtime.
   If some text must stay in the source, emit it ONLY via JSON.stringify(value) as a string
   literal (never inside comments, template literals, or identifiers).
2. Comments: remove user text from comments, or sanitize by replacing \r, \n,  ,   and
   "*/" and limiting length.
3. Validate the request body with a schema (use the validation library the repo already uses,
   e.g. zod/joi; otherwise hand-written checks): types, max lengths, max number of test cases and
   steps; ids must match a safe pattern like ^[A-Za-z0-9._-]{1,100}$. Reject with 400.
4. File names/paths: build from validated ids only, resolve and verify the final path stays
   inside the Playwright test directory (path.resolve + startsWith check).
5. Generated specs must not be executable until reviewed: add a status to catalog entries
   (e.g. "pending_review" | "approved"); generate-spec creates "pending_review";
   script-catalog execution route refuses anything not "approved" (409). Approval requires an
   approver role (use the existing role helper if there is one; SEC-2 will harden auth).
6. Tests: unit tests proving that inputs containing "\n", "*/", "`", "${", "');", " "
   in every field produce a spec whose code is identical to a spec built with safe inputs
   (only the JSON data differs), and that execution of a pending spec is rejected.

RULES
- Show me the list of files you will change and your design before editing; wait for my OK.
- Match the existing code style and error handling. No unrelated refactoring.
- Do not change S3/storage code. Do not add new dependencies without asking.
- At the end: summary of changes, how to test manually, and any remaining risk.
```

## SEC-2 — No production authentication gate; missing route authorization (Critical)

```
#codebase
Branch: fix/sec-2-authn-authz

PROBLEM (from security audit)
- identity.middleware.ts ~43: in production, missing identity headers produce an "anonymous"
  viewer identity and the request continues.
- mutation-guard.middleware.ts ~7: the guard only checks Origin; requests WITHOUT an Origin
  header continue (so curl/server-side calls bypass it).
- Sensitive routes do not consistently enforce roles: test execution (tests.route.ts ~25),
  repository writes (test-repository.route.ts ~158), approvals/release decisions
  (lifecycle.route.ts ~183, ~362), script execution (script-catalog.route.ts ~51).
- Deployment: ECS Express Mode behind an ALB. Env vars: SAGE_ALLOW_DEVELOPMENT_IDENTITY (false in
  ECS), SAGE_TRUST_IDENTITY_HEADERS, CORS_ORIGINS. sage-api calls this service server-to-server
  (NODE_API_BASE_URL), so those calls have no browser Origin. An Okta-backed session is planned.

STEP 1 — REPORT FIRST (no edits)
Explain how identity works today: where identity comes from (headers/cookies/tokens), which
headers are trusted, how roles are represented, which routes exist (method + path + current
checks), and how sage-api and the browser UI call this service. Produce a route table:
method | path | action type (read/write/execute/approve/admin) | current check | proposed role.
Wait for my confirmation before Step 2.

STEP 2 — IMPLEMENT
1. Fail closed in production: if NODE_ENV=production and no verified identity -> 401. The
   anonymous/development identity is allowed only when NODE_ENV!=production AND
   SAGE_ALLOW_DEVELOPMENT_IDENTITY=true. Keep /api/health public.
2. Identity headers are trusted only when SAGE_TRUST_IDENTITY_HEADERS=true AND the request is
   proven to come from the trusted proxy (e.g. verify a signed header such as the ALB
   x-amzn-oidc-data JWT, or a shared secret header from env). Otherwise ignore those headers.
3. Service-to-service calls from sage-api: require a token (e.g. Authorization: Bearer <secret
   from env SAGE_SERVICE_TOKEN>, compared with crypto.timingSafeEqual) instead of relying on a
   missing Origin. Tell me the env var name you pick so I can add it to deploy-node.yml secrets.
4. Mutation guard: for state-changing methods (POST/PUT/PATCH/DELETE), requests from browsers must
   have an Origin in CORS_ORIGINS; requests without Origin must carry the service token; otherwise
   403.
5. Add a requireRole(...roles) middleware (or reuse an existing helper) and apply it per the
   route table from Step 1: read = viewer, write = editor, execute = runner/editor,
   approve/release = approver, admin actions = admin (use the role names that already exist).
6. Update deploy-node.yml environment-variables/secrets for any new env var (no hardcoded values)
   and the pre-flight check step.
7. Tests: anonymous request in production -> 401; spoofed identity headers without trusted proxy
   proof -> ignored; POST without Origin and without service token -> 403; viewer calling
   execute/approve routes -> 403; correct role -> 200.

RULES
- Show the file list before editing; wait for my OK.
- Do not break local development: with NODE_ENV!=production and
  SAGE_ALLOW_DEVELOPMENT_IDENTITY=true the app must keep working as today.
- Match existing style. No unrelated refactoring. Don't add dependencies without asking.
- At the end: summary, env vars I must configure in GitHub/ECS, manual test steps.
```

## SEC-3 — SSRF: browser automation routes accept any URL (High)

```
#codebase
Branch: fix/sec-3-ssrf-url-policy

PROBLEM (from security audit)
Explorer (explorer.route.ts ~47), Recorder (recorder.route.ts ~52) and AI Driver
(ai-driver.route.ts ~21) accept caller-supplied URLs and navigate to them from the server with
Playwright. The existing target URL policy (url-policy.ts ~49) is only used by one agentic tool
(tool-registry.ts ~216). The service runs on AWS ECS, so http://169.254.169.254 and
169.254.170.2 (task metadata/credentials), localhost, and VPC-internal hosts are reachable.

FIX
1. Extend url-policy.ts into one shared validator used by ALL entry points above (and any other
   route or tool that navigates/fetches a user URL — search the repo, including the AI Driver
   Python hand-off and Figma/Jira if they take user URLs):
   - allow only http/https; no credentials in URL; optional host allowlist from env
     SAGE_ALLOWED_TARGET_HOSTS (comma-separated, supports *.example.com).
   - resolve DNS and block loopback, private (10/8, 172.16/12, 192.168/16), link-local
     (169.254/16 incl. 169.254.169.254 and 169.254.170.2), CGNAT 100.64/10, 0.0.0.0/8,
     multicast, IPv6 ::1, fc00::/7, fe80::/10, IPv4-mapped IPv6; handle decimal/octal/hex IP
     forms. Use Node's net.BlockList or ipaddr.js if already a dependency.
2. Enforce during browsing, not only at the start: add a Playwright context.route('**/*')
   handler that validates every request URL (navigations, redirects, subresources, popups) and
   aborts blocked ones. Also check page.on('framenavigated') / redirects.
3. Return 400 with a clear message for rejected targets; log the rejection (without logging
   secrets).
4. Tests: blocked for http://169.254.169.254/latest/meta-data, http://localhost:5000,
   http://127.1, http://0x7f000001, http://[::1], http://10.0.0.5, a hostname resolving to a
   private IP, and a public URL that redirects to a blocked one; allowed for a public host.
5. Write in the summary the infra follow-up for me (do not implement): restrict ECS task
   security-group egress, and set ECS task metadata protection where possible.

RULES
- Show the file list before editing; wait for my OK.
- Match existing style; no unrelated refactoring; ask before adding dependencies.
- In local development keep the same policy, but allow localhost only if env
  SAGE_ALLOW_LOCAL_TARGETS=true and NODE_ENV!=production.
```

## SEC-4 — Cross-user mission disclosure + vulnerable spreadsheet parser (High)

```
#codebase
Branch: fix/sec-4-missions-and-xlsx

PROBLEM A (from security audit)
GET /api/agentic/missions?mine=false: the route (agentic.route.ts ~70) omits the owner filter
when mine=false even for non-admins, and the store (mission.store.ts ~42) then returns all
missions. Missions may contain sensitive goals, evidence and tool results.

FIX A
1. Always apply the owner filter from the server-derived identity (never from a query param or
   body). Only an admin role may list other users' missions (mine=false or ownerId=...).
   Non-admin with mine=false -> either 403 or silently own-only (tell me which fits the UI; default 403).
2. Apply the same owner check to get/update/delete of a single mission by id (404 if not owner
   and not admin, to avoid leaking existence).
3. Tests for owner, other user, admin.

PROBLEM B (from security audit)
Root dependency xlsx@0.18.5 (package.json ~72) has prototype-pollution and ReDoS advisories; no
fix exists on npm for that line. Workbooks are parsed with XLSX.read in
manual-test-import.service.ts ~225.

FIX B
1. Report first: every place xlsx is imported and which features are used (read only? write?
   csv? formulas? styles?). Then propose ONE option and wait for my OK:
   a) exceljs (maintained on npm) for .xlsx + a CSV parser already in the repo (or csv-parse), or
   b) the patched SheetJS build from the official SheetJS CDN (xlsx 0.20.x tarball URL in
      package.json).
2. Whatever the library, add limits: max upload size (e.g. 10 MB, env configurable), reject
   zip bombs (max total uncompressed size / max entries), max sheets/rows/columns/cell length,
   parse in a worker_thread with a timeout and memory limit, only accept .xlsx/.csv by
   extension AND magic bytes, never evaluate formulas, and build row objects with
   Object.create(null) or reject keys "__proto__", "constructor", "prototype".
3. Keep the existing import output format identical; add tests with a normal file, an
   oversized file, a file with a "__proto__" header, and a malformed file.
4. Run npm audit and show the result.

RULES
- Show the file list before editing; wait for my OK.
- Match existing style; no unrelated refactoring.
```

## SEC-5 — Audit key, test-run timeout cleanup, blocking Python calls (Medium)

```
#codebase
Branch: fix/sec-5-audit-process-async

PROBLEM 1 — Audit integrity (finding 9)
Without SAGE_AUDIT_HMAC_KEY, tamper-evident-audit.ts (~20) falls back to a hard-coded
development key, so production could produce forgeable audit chains.
FIX 1: In production (NODE_ENV=production) the app must refuse to start if SAGE_AUDIT_HMAC_KEY is
missing or shorter than 32 bytes (clear error log). The dev key is allowed only when
NODE_ENV!=production. Apply the same rule to SAGE_DATA_ENCRYPTION_KEY if it has a fallback.
Never log key values. Add a startup test. Add an audit-chain verify function/endpoint for
admins if one does not exist (tell me first).

PROBLEM 2 — Playwright timeout does not reliably stop execution (finding 7)
In test-run.tool.ts (~164) the timeout sends SIGTERM, schedules a guarded SIGKILL, then
immediately calls finish(), which sets settled=true; the delayed kill checks !settled and
therefore never runs. Child processes (browsers) may survive.
FIX 2: Spawn the test process in its own process group (detached: true on Linux) and on timeout:
kill the whole group (process.kill(-pid, 'SIGTERM')), wait a grace period, then SIGKILL the group
if it is still alive (independent of "settled"), wait for the 'exit'/'close' event, and only then
finalize the run with status "timeout". On Windows use taskkill /pid <pid> /T /F. Make finish()
idempotent. Test with a fake long-running child that spawns a grandchild.

PROBLEM 3 — Python readiness analysis blocks the event loop (finding 8)
evaluateStoryReadiness uses spawnSync (story-readiness.tool.ts ~67); Jira analysis may process up
to 50 issues sequentially (jira.route.ts ~58), blocking the whole server.
FIX 3: Replace spawnSync with async spawn wrapped in a Promise with timeout (kill on timeout,
same group-kill helper as Fix 2), max stdout size, and limited concurrency (e.g. 3–4 at a time,
env configurable; use p-limit only if already a dependency, otherwise a small helper). If a
request may take long, return 202 with a job id and a status endpoint — tell me first if that
changes the UI contract; otherwise keep the response shape.

RULES
- Show the file list before editing; wait for my OK.
- Match existing style; no unrelated refactoring; ask before adding dependencies.
```

manual-test-imports/). Log counts. Test with an expired and a non-expired import.
