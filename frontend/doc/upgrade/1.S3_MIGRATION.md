# S3 Storage Upgrade — sage-node (Phase 1 / Version 1: S3 only)

> **This is not a data migration.** There is no existing local data that needs to be preserved,
> backfilled, or cut over — local disk storage on the ECS task is already ephemeral and doesn't
> survive a task replacement today, so nothing of value sits there to carry forward. This document
> covers **upgrading where the application writes going forward**: new artifacts go to S3 instead
> of local disk, starting from the next deploy. Don't write, and don't ask Copilot to write, any
> backfill/copy-existing-files logic — there's nothing to copy.
>
> Scope: this document covers **Phase 1 only** — writing file/binary artifacts to Amazon S3
> instead of the ECS task's local disk. PostgreSQL is **not** part of this document; see
> [2.POSTGRES_MIGRATION.md](2.POSTGRES_MIGRATION.md) for Phase 2, which must not be deployed
> together with this phase.
>
> Source material for this document: the `Dockerfile` and `.github/workflows/deploy-node.yml`
> shared via screenshots in this session, plus the storage-path list given earlier in this
> conversation. **I do not have access to the sage-node application source code** (`server.ts`,
> the module that currently performs local file reads/writes, `python/ai_driver.py`,
> `python/story_readiness_analyzer.py`). Anywhere this document needs to reference that code, it
> is explicitly flagged under [Assumptions / Items Requiring Confirmation](#assumptions--items-requiring-confirmation)
> rather than guessed.

## 1. Current architecture

```
Browser / sage-ui / sage-api
        |
        v
  sage-node (ECS Fargate task, Express Mode, 1 task, no horizontal scaling)
        |
        v
  Local container filesystem (/app/...)
        |
        +-- results-store/        lifecycle, test repo, agentic missions, Ask SAGE sessions,
        |                         audits, Quality Graph, reconciliation data
        +-- recorded-tests/       recorded tests and screenshots
        +-- test-reports/         execution reports
        +-- explorer-reports/     Explorer crawl results
        +-- figma-reports/        Figma analysis results
        +-- ai-driver-artifacts/  AI Driver screenshots, videos, artifacts
```

This is **ephemeral**: nothing under these paths survives a task replacement (deploy, crash,
circuit-breaker rollback, scaling event). There is currently no EFS or database configured in the
Express Mode workflow. `min-task-count`/`max-task-count` are both pinned to `1` specifically
*because* these are local JSON/NDJSON stores that are not safe to run behind more than one task
(per the comment already in `deploy-node.yml`).

External data (Jira issues, Figma data, Azure OpenAI requests) is not part of this migration — it
stays in those external services per their own APIs.

## 2. Target architecture (Phase 1)

```
sage-node (ECS Fargate task)
        |
        v
  Amazon S3  (bucket: <S3_BUCKET_NAME>, prefix: sage/)
        |
        +-- sage/results-store/
        +-- sage/recorded-tests/
        +-- sage/test-reports/
        +-- sage/explorer-reports/
        +-- sage/figma-reports/
        +-- sage/ai-driver-artifacts/
```

```
Before
   ↓
Local file storage (/app/results-store, /app/recorded-tests, ...) — lost on task replacement

After Phase 1
   ↓
Amazon S3 (s3://<bucket>/sage/<category>/...) — durable, independent of task lifecycle
```

PostgreSQL is **not** introduced in this phase. The structured/queryable portion of
`results-store` (audits, Quality Graph, reconciliation data) still lands in S3 as files in Phase
1; Phase 2 is what moves that subset into PostgreSQL. Don't defer Phase 1 waiting on that — file
storage in S3 works identically whether or not Phase 2 ever happens.

## 3. S3 folder / prefix structure

Single parent prefix, one sub-prefix per existing local folder — no new categories invented:

```
s3://<S3_BUCKET_NAME>/sage/
├── results-store/
├── recorded-tests/
├── test-reports/
├── explorer-reports/
├── figma-reports/
└── ai-driver-artifacts/
```

These are **S3 prefixes, not real folder objects** — S3 has no native directories. Nothing needs
to be pre-created; the prefix appears the moment the first object is written under it (e.g.
`sage/recorded-tests/2026-09-24/run-42.png`). The automation script in
[AUTOMATED_INFRA_SETUP.md](AUTOMATED_INFRA_SETUP.md) does not create placeholder objects for this
reason, unless the application specifically expects a zero-byte marker object per prefix (not
currently known — see Assumptions).

## 4. Application changes

**What's confirmed:** six local paths listed above map 1:1 to S3 prefixes under `sage/`.

**What's not confirmed (no source access):**
- Which exact module(s) perform the `fs.writeFile` / `fs.readFile` / `fs.readdir` / `fs.unlink`
  calls against these paths today.
- Whether file paths are constructed in one central storage helper or scattered across routes
  (Explorer, Recorder, AI Driver, Figma, Ask SAGE — per the workflow's own description of this
  service).
- Whether any of these files are read back *synchronously* on the hot request path (S3 GETs add
  network latency that local disk reads don't have — this can matter for a "download report" type
  endpoint).
- Whether `results-store` is read via full-directory scans (`fs.readdir`) anywhere — S3 has no
  direct equivalent; that becomes a `ListObjectsV2` call with a prefix, which is a different
  access pattern from listing a local directory.

**Recommended approach**, to be applied once the actual storage code is available: introduce one
storage abstraction (e.g. `src/storage/artifactStore.ts`) that exposes `put`, `get`, `list`,
`delete` and route every existing `fs.*` call for these six paths through it. The implementation
swaps from local `fs` calls to `@aws-sdk/client-s3` (`PutObjectCommand`, `GetObjectCommand`,
`ListObjectsV2Command`, `DeleteObjectCommand`) with the key prefixed by `S3_BASE_PREFIX/<category>`.
This is a source-code change and is **not performed in this session** — flagged per your
instruction not to modify source code without being able to explain exactly why, which requires
seeing the code first.

## 5. Docker changes

**None required.** The AWS SDK for JavaScript v3 (`@aws-sdk/client-s3`) is a pure npm package —
no OS-level packages, no Dockerfile stage changes. It gets added via `package.json` (already
covered by the existing `RUN npm ci` / `RUN npm ci --omit=dev` steps) and picks up credentials
automatically from the ECS task metadata endpoint at runtime — no baked-in keys, no Dockerfile
`ENV` for credentials.

The one existing Dockerfile line worth noting for later cleanup (not removed yet, per "don't
remove functionality until S3 is confirmed working"):
```dockerfile
RUN useradd --create-home --uid 10001 sage && mkdir -p /app/data && chown -R sage:sage /app
```
`/app/data` is referenced elsewhere in the deploy workflow as `PLAYWRIGHT_REPO_PATH` — that's a
separate concern from the six artifact folders above and is **out of scope** for this migration
unless confirmed otherwise (see Assumptions).

## 7. IAM requirements

New IAM role: **`sage-ecs-task-role`** (name chosen to match the naming convention already
guarded against in the existing script's `case` statement — confirm whether this role already
exists for sage-api/sage-ui before creating a new one; see Assumptions).

Trust policy (allows ECS tasks to assume it):
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ecs-tasks.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

Permissions policy, scoped to the `sage/` prefix only (least privilege — not full-bucket access):
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListSagePrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::<S3_BUCKET_NAME>",
      "Condition": { "StringLike": { "s3:prefix": "sage/*" } }
    },
    {
      "Sid": "ReadWriteSageObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::<S3_BUCKET_NAME>/sage/*"
    }
  ]
}
```
Drop `s3:DeleteObject` if the application never deletes/overwrites artifacts (unconfirmed — see
Assumptions). Granting it and never using it is low-risk; not granting it when the app needs it
produces a hard runtime failure, so the default above includes it.

## 8. AWS credentials / authentication mechanism

**Currently**: none exist for AWS API calls from *inside* the running container — only the
GitHub Actions OIDC role (`AWS_DEPLOY_ROLE_ARN`) authenticates the CI pipeline to push images and
deploy. The container itself has no AWS identity today.

**After this change**: the container authenticates via the ECS **task role**
(`sage-ecs-task-role`, wired through the new `task-role-arn` input). The AWS SDK inside the app
auto-discovers these credentials from the ECS container credentials endpoint
(`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, set automatically by the ECS agent) — no access keys,
no secrets, nothing to configure in `package.json` or Dockerfile beyond installing the SDK.

## 9. Deployment target

Confirmed from the existing workflow: **Amazon ECS Fargate**, deployed via ECS **Express Mode**
(`aws-actions/amazon-ecs-deploy-express-service@v1`), not EC2-backed ECS, not Lambda.

## 10. Required S3 permissions

Read, write, and delete (see IAM policy above) — no `PutBucketPolicy`/admin-level bucket
permissions needed by the application itself; those are one-time setup actions performed by
infrastructure automation (see [AUTOMATED_INFRA_SETUP.md](AUTOMATED_INFRA_SETUP.md)), not by the
running application.

## 11. Volume configuration made unnecessary

None currently exists to remove — the local Docker-only `docker run -v ...` bind mounts described
earlier in this project are a **local development convenience only** and are not part of the ECS
deployment (Express Mode has no EFS/volume configured). Nothing in `deploy-node.yml` or the
Dockerfile needs volume removal. Local `docker run` development workflows can keep using bind
mounts unchanged — Phase 1 doesn't need to touch local dev ergonomics, only the deployed
environment's persistence model.

## 12. Deployment steps

1. Create/confirm `sage-ecs-task-role` and its S3 policy (via automation script or manually — see
   [AUTOMATED_INFRA_SETUP.md](AUTOMATED_INFRA_SETUP.md)).
2. Create/confirm the S3 bucket (`S3_BUCKET_NAME`) exists, with default encryption and public
   access block enabled.
3. Add repository secret `ECS_TASK_ROLE_ARN` and variables `S3_BUCKET_NAME`, `S3_BASE_PREFIX`
   in GitHub (Settings → Secrets and variables → Actions).
4. Apply the `deploy-node.yml` changes in [Section 6](#6-yaml-changes-deploy-nodeyml).
5. Apply the application storage-layer code change (blocked — needs source access; see
   [Section 4](#4-application-changes)).
6. Push to `main`/`master` (or run `workflow_dispatch`) to trigger build + deploy.
7. Run the validation procedure below.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `AccessDenied` on PutObject/GetObject | Task role policy doesn't cover the exact key/prefix, or `task-role-arn` wasn't actually wired into the deploy step | Confirm the object key starts with `sage/`; confirm the deployed task definition shows a `taskRoleArn` (ECS console → Task definitions → latest revision) |
| `NoSuchBucket` | Wrong `S3_BUCKET_NAME`, wrong region, or bucket not yet created | `aws s3api head-bucket --bucket <name> --region <region>` to confirm it exists in that account/region |
| Incorrect region | SDK defaults to a region that doesn't match the bucket | Ensure `AWS_REGION` env var is present in the task (see Section 6D) and matches the bucket's actual region |
| IAM permission issues (assume-role denied) | Task role's trust policy doesn't trust `ecs-tasks.amazonaws.com`, or `task-role-arn` input typo'd | Re-check the trust policy JSON in Section 7; confirm the ARN in the `ECS_TASK_ROLE_ARN` secret is exact |
| Incorrect prefix (objects land outside `sage/`) | `S3_BASE_PREFIX` unset/mistyped, or app code not prefixing keys | Confirm the repository variable is set; confirm the app's key-construction logic (once available) actually applies the prefix |
| Credentials not available at runtime | Task role not attached (older task definition revision still running), or code using long-lived keys instead of the default SDK credential chain | Force a new deployment; confirm no `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars were hand-set anywhere (they'd shadow the task role) |
| Docker environment configuration issues | `AWS_REGION`/`S3_BUCKET_NAME` missing from `environment-variables` JSON | Re-check Section 6C was applied exactly; a missing var here is silent until the app tries to use it |
| ECS task role issues (role not found) | Role not yet created, or created in the wrong account | Run the automation script's validate step, or `aws iam get-role --role-name sage-ecs-task-role` |
| Application unable to upload/download despite correct IAM | SDK region mismatch, VPC endpoint misconfiguration (if outbound internet is restricted), or the app still pointed at local paths | Check CloudWatch logs for the actual SDK error message; confirm whether this VPC has an S3 Gateway VPC Endpoint if outbound internet access is restricted |

## Rollback

Phase 1 is additive — the `task-role-arn` and new env vars only take effect once the application
code actually calls S3, which isn't part of this document's scope yet. Until the storage-layer
code change ships:
- Reverting `deploy-node.yml` to its previous version (drop the three additions in Section 6) is a
  safe, immediate rollback — nothing depends on the new secret/variables existing.
- Once the code change ships and is deployed, rollback is: redeploy the previous image tag
  (`docker/build-push-action` tags every build with `${{ github.sha }}` — redeploy an earlier SHA
  via `workflow_dispatch` against that tag, or `aws ecs update-service --force-new-deployment`
  after manually pointing the task definition at the prior image) while leaving local-disk code
  paths intact until S3 is fully validated (per your instruction: don't remove local-storage
  functionality until S3 integration is confirmed).

## Production considerations

- The bucket should have **default server-side encryption (SSE-S3 or SSE-KMS)** and **Block
  Public Access enabled** — these are artifacts that may include audit data.
- Consider **S3 Versioning** if accidental overwrite/delete protection matters for audit
  artifacts — not currently confirmed as a requirement (see Assumptions).
- Add **S3 Lifecycle rules** for cost control once volume is understood in production (see the
  [Sage Storage Architecture](https://claude.ai/artifact/T4QYZZ6GzeBQvNswoak9HG) artifact shared
  earlier in this session for the specific transition tiers/pricing).
- `max-task-count: 1` remains unchanged by this migration — S3 itself doesn't remove the
  single-task constraint, since that constraint is about the *other* local state (JSON/NDJSON
  stores), not just file artifacts. Don't scale this service past 1 task based on this migration
  alone; that's a separate decision tied to whatever remains local after Phase 2.
- DEV/UAT/PROD: use separate buckets (or at minimum separate `S3_BASE_PREFIX` values, though
  separate buckets are strongly preferred) per environment so a UAT test run can never write into
  a PROD bucket. Confirm the existing `ECS_CLUSTER` naming pattern (`sage-dev` seen in the
  workflow) for the equivalent bucket-naming convention.

## Assumptions / Items Requiring Confirmation

1. **`sage-ecs-task-role` may already exist.** The existing `deploy-node.yml` script guards
   against `ECS_INFRASTRUCTURE_ROLE_ARN` being mistakenly set to `*sage-ecs-task-role`, which
   implies this role name is already an established convention in this project (possibly created
   for sage-api or sage-ui already). **Confirm in IAM before running the creation script** —
   reuse if it exists, rather than creating a duplicate.
2. **Storage code location and structure are unknown.** No access to `server.ts` or the module(s)
   performing local file I/O. Section 4's storage-abstraction recommendation is a pattern to
   apply once that code is available, not a change made in this session.
3. **`s3:DeleteObject` necessity is unconfirmed.** Included in the default IAM policy on the
   assumption that some workflow (re-running a test, replacing a report) overwrites/deletes an
   existing object; confirm against actual app behavior and remove if unused.
4. **Bucket naming convention is unconfirmed.** No existing S3 bucket name was visible anywhere
   in the shared files. A suggested convention (e.g. `sage-<env>-<account-id>`) is used in the
   automation script as a *default*, not a hardcoded requirement — confirm against whatever
   convention your AWS account structure already uses for bucket names (if any).
5. **`/app/data` (used for `PLAYWRIGHT_REPO_PATH`) is out of scope.** Not one of the six listed
   artifact categories; not touched by this migration unless you confirm it should be.
6. **Whether `results-store` needs directory-listing behavior (`fs.readdir`) is unconfirmed.** If
   so, the S3 equivalent (`ListObjectsV2`) has different pagination/consistency semantics that the
   storage-abstraction code will need to account for — flagged for whoever implements Section 4.
7. **Versioning/retention requirements for audit-related artifacts are unconfirmed** — worth a
   compliance check given `audits` and `Quality Graph` live under `results-store`.
