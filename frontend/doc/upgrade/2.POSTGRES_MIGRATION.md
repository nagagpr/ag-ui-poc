# PostgreSQL Storage Upgrade — sage-node (Phase 2 / Version 2: S3 + PostgreSQL)

> **This is not a data migration.** There is no existing database, and the structured data
> currently living in local JSON/NDJSON files is not being preserved or converted — it's ephemeral
> today (lost on every task replacement, same as the S3-bound artifacts in Phase 1). This document
> covers **implementing PostgreSQL as where this structured data gets written going forward**,
> starting from a clean, empty schema. Don't write, and don't ask Copilot to write, any logic that
> reads old local JSON/NDJSON files and imports their contents into Postgres — there's nothing
> that needs importing. The `db/migrations/*.sql` files create empty tables; the application starts
> populating them from its next deploy onward.
>
> **Do not deploy this together with Phase 1.** This document only makes sense *after*
> [1.S3_MIGRATION.md](1.S3_MIGRATION.md) (Version 1) has been deployed and validated. Everything
> below is additive on top of Version 1 — changes marked **NEW vs. Version 1** are the only things
> this phase adds; nothing from Phase 1 is removed or replaced.
>
> Same source caveat as Phase 1: no access to the sage-node application source code. The schema in
> this document is a **proposal derived from the category names already described in this
> conversation** (lifecycle, test repository, agentic missions, Ask SAGE sessions, audits, Quality
> Graph, reconciliation data) — not something read out of real code. Treat every table/column
> below as a draft to validate against the actual data shapes before implementing against a real
> environment.

## 1a. One-time manual setup: RDS instance, security group, Secrets Manager

Infrastructure automation ([AUTOMATED_INFRA_SETUP.md](AUTOMATED_INFRA_SETUP.md) /
`scripts/setup-postgres.sh`) is being skipped for this integration. These are the exact,
copy-pasteable commands to run once, by hand, so the pieces this phase depends on actually exist.
Run them with an AWS CLI profile authenticated against the account `sage-node`'s ECS service runs
in (cluster `sage`, region `us-east-1`, confirmed earlier in this session).

**Step 1 — discover the real VPC and CIDR (don't hardcode these):**
```bash
# These six subnet IDs are the ones already attached to the sage-node ECS service today
# (confirmed from the service's own Networking configuration in the ECS console).
SUBNET_IDS="subnet-0a6c9d4d4a56eb401 subnet-0f9b5a62639d8ccfa subnet-011b0aee80c2b8c97 subnet-0e317e82158e271be subnet-0c4c318e6c2a475f2 subnet-045a5cf2bdafd349b"
REGION="us-east-1"

VPC_ID=$(aws ec2 describe-subnets --region "$REGION" \
  --subnet-ids $(echo $SUBNET_IDS | cut -d' ' -f1) \
  --query 'Subnets[0].VpcId' --output text)
echo "VPC: $VPC_ID"

VPC_CIDR=$(aws ec2 describe-vpcs --region "$REGION" --vpc-ids "$VPC_ID" \
  --query 'Vpcs[0].CidrBlock' --output text)
echo "VPC CIDR: $VPC_CIDR"
```
If `ECS_SUBNETS` is ever explicitly set to something different, re-run this discovery against
those subnet IDs instead of reusing values from a prior run.

**Step 2 — create the DB subnet group** (RDS requires at least 2 subnets in different AZs; skip
if `aws rds describe-db-subnet-groups --db-subnet-group-name sage-dev-db-subnets --region "$REGION"`
already returns one):
```bash
aws rds create-db-subnet-group \
  --region "$REGION" \
  --db-subnet-group-name sage-dev-db-subnets \
  --db-subnet-group-description "sage-node PostgreSQL - dev" \
  --subnet-ids $SUBNET_IDS
```

**Step 3 — create the security group and ingress rule:**
```bash
SG_ID=$(aws ec2 create-security-group \
  --region "$REGION" \
  --group-name sage-dev-postgres-sg \
  --description "sage-node PostgreSQL - dev" \
  --vpc-id "$VPC_ID" \
  --query GroupId --output text)
echo "Security group: $SG_ID"

aws ec2 authorize-security-group-ingress \
  --region "$REGION" \
  --group-id "$SG_ID" \
  --protocol tcp --port 5432 \
  --cidr "$VPC_CIDR"
```
This opens port 5432 to the whole VPC CIDR — acceptable for dev, since nothing outside this VPC
can reach it regardless. Narrow this to a specific subnet CIDR, or (once it's known — see the
Section 13 note) the ECS service's own auto-created security group ID, before doing this in
production.

**Step 4 — store the master password in Secrets Manager:**
```bash
DB_PASSWORD=$(aws secretsmanager get-random-password --region "$REGION" \
  --password-length 32 --exclude-punctuation --query RandomPassword --output text)

aws secretsmanager create-secret \
  --region "$REGION" \
  --name sage-node/dev/postgres \
  --description "sage-node PostgreSQL master credentials (dev)" \
  --secret-string "{\"username\":\"sage_admin\",\"password\":\"${DB_PASSWORD}\"}"

SECRET_ARN=$(aws secretsmanager describe-secret --region "$REGION" \
  --secret-id sage-node/dev/postgres --query ARN --output text)
echo "Secret ARN: $SECRET_ARN"
```
`$DB_PASSWORD` stays in this shell session only — never echo it to a log, terminal history you'll
share, or commit it anywhere. Only the ARN gets pasted into GitHub (Section 7).

**Step 5 — create the RDS instance** (takes 5–10 minutes):
```bash
aws rds create-db-instance \
  --region "$REGION" \
  --db-instance-identifier sage-dev-postgres \
  --db-instance-class db.t4g.micro \
  --engine postgres \
  --master-username sage_admin \
  --master-user-password "$DB_PASSWORD" \
  --allocated-storage 20 \
  --db-name sage \
  --db-subnet-group-name sage-dev-db-subnets \
  --vpc-security-group-ids "$SG_ID" \
  --no-publicly-accessible \
  --backup-retention-period 7 \
  --storage-encrypted

aws rds wait db-instance-available --region "$REGION" --db-instance-identifier sage-dev-postgres
```

**Step 6 — retrieve the endpoint and run migrations:**
```bash
DB_HOST=$(aws rds describe-db-instances --region "$REGION" \
  --db-instance-identifier sage-dev-postgres \
  --query 'DBInstances[0].Endpoint.Address' --output text)
DB_PORT=$(aws rds describe-db-instances --region "$REGION" \
  --db-instance-identifier sage-dev-postgres \
  --query 'DBInstances[0].Endpoint.Port' --output text)
echo "DB_HOST=$DB_HOST"
echo "DB_PORT=$DB_PORT"

export PGPASSWORD="$DB_PASSWORD"
psql -h "$DB_HOST" -p "$DB_PORT" -U sage_admin -d sage -f db/migrations/0001_init_schema.sql
psql -h "$DB_HOST" -p "$DB_PORT" -U sage_admin -d sage -f db/migrations/0002_indexes.sql
unset PGPASSWORD
```
Run this from somewhere that can actually reach the VPC — RDS is `--no-publicly-accessible`, so
the same private-network constraint covered earlier in this project (VPN, a bastion/EC2 inside the
VPC, or a CloudShell VPC environment) applies here too. A plain terminal on your laptop will not
be able to reach `$DB_HOST` directly.

You now have every value Section 7 needs: `SECRET_ARN` → `DB_SECRET_ARN`, `DB_HOST`, `DB_PORT`
(`5432`), and `DB_NAME` (`sage`).

```
                                             ↓

```

```
        |
```

## 3. Data classification

```
S3
----
Files, images, videos, reports, artifacts, large objects, binary data
  recorded-tests/*.png, *.webm
  test-reports/*.html, *.json
  explorer-reports/*
  figma-reports/*
  ai-driver-artifacts/*
  (any large payload referenced FROM a Postgres row via an S3 key, never stored inline)

PostgreSQL
----------
Metadata, application records, relationships, status, configuration,
structured/queryable data, audit information
  lifecycle state
  test-repository entries (pointers to S3 objects, not the objects themselves)
  agentic mission records
  Ask SAGE session transcripts/metadata
  audits (HMAC-signed — see Section 4 note)
  Quality Graph (nodes + edges)
  reconciliation records
```

No large binaries are stored in PostgreSQL — every table below that references an artifact stores
an **S3 key** (`sage/<category>/<...>`), not the file itself.

## 4. PostgreSQL schema (proposed — confirm against real data model)

Two existing environment variables in `deploy-node.yml` — `SAGE_DATA_ENCRYPTION_KEY` and
`SAGE_AUDIT_HMAC_KEY` — indicate the application **already encrypts and/or HMAC-signs some data at
the application layer** before persisting it. This schema assumes that pattern continues
unchanged: Postgres stores whatever encrypted/signed value the app already produces (as `bytea` or
`text`), rather than this migration introducing its own encryption scheme. Confirm this against
the actual code before implementing.

```sql
-- Schema: sage (dedicated schema, not "public", to keep this isolated from other services
-- that may eventually share the same RDS instance)
CREATE SCHEMA IF NOT EXISTS sage;

-- Lifecycle: state machine / status tracking referenced by "lifecycle" in results-store
CREATE TABLE sage.lifecycle_events (
    id              BIGSERIAL PRIMARY KEY,
    entity_type     TEXT NOT NULL,          -- e.g. 'test', 'mission', 'session'
    entity_id       TEXT NOT NULL,
    status          TEXT NOT NULL,
    metadata        JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_lifecycle_events_entity ON sage.lifecycle_events (entity_type, entity_id);

-- Test repository: metadata for recorded tests; binary content lives in S3
CREATE TABLE sage.test_repository (
    id              BIGSERIAL PRIMARY KEY,
    name            TEXT NOT NULL,
    description     TEXT,
    s3_key          TEXT NOT NULL,          -- sage/recorded-tests/...
    status          TEXT NOT NULL DEFAULT 'active',
    created_by      TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Agentic missions
CREATE TABLE sage.agentic_missions (
    id              BIGSERIAL PRIMARY KEY,
    mission_type    TEXT NOT NULL,
    status          TEXT NOT NULL,
    input           JSONB,
    result          JSONB,
    s3_report_key   TEXT,                   -- optional pointer into ai-driver-artifacts/ or test-reports/
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at     TIMESTAMPTZ
);

-- Ask SAGE sessions
CREATE TABLE sage.ask_sage_sessions (
    id              BIGSERIAL PRIMARY KEY,
    user_identity   TEXT,
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    ended_at        TIMESTAMPTZ,
    metadata        JSONB
);

CREATE TABLE sage.ask_sage_messages (
    id              BIGSERIAL PRIMARY KEY,
    session_id      BIGINT NOT NULL REFERENCES sage.ask_sage_sessions(id) ON DELETE CASCADE,
    role            TEXT NOT NULL,          -- 'user' | 'assistant'
    content         TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ask_sage_messages_session ON sage.ask_sage_messages (session_id);

-- Audits: HMAC-signed, append-only. hmac_signature computed with SAGE_AUDIT_HMAC_KEY.
CREATE TABLE sage.audits (
    id              BIGSERIAL PRIMARY KEY,
    entity_type     TEXT NOT NULL,
    entity_id       TEXT NOT NULL,
    action          TEXT NOT NULL,
    actor           TEXT,
    payload         JSONB NOT NULL,
    hmac_signature  TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_audits_entity ON sage.audits (entity_type, entity_id);
-- No UPDATE/DELETE grants on this table for the app role (see Section 12) — audits are append-only.

-- Quality Graph: nodes + edges (a graph modeled relationally)
CREATE TABLE sage.quality_graph_nodes (
    id              TEXT PRIMARY KEY,       -- caller-assigned stable node id
    node_type       TEXT NOT NULL,
    properties      JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE sage.quality_graph_edges (
    id              BIGSERIAL PRIMARY KEY,
    source_id       TEXT NOT NULL REFERENCES sage.quality_graph_nodes(id) ON DELETE CASCADE,
    target_id       TEXT NOT NULL REFERENCES sage.quality_graph_nodes(id) ON DELETE CASCADE,
    relationship    TEXT NOT NULL,
    properties      JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_qg_edges_source ON sage.quality_graph_edges (source_id);
CREATE INDEX idx_qg_edges_target ON sage.quality_graph_edges (target_id);

-- Reconciliation records
CREATE TABLE sage.reconciliation_records (
    id              BIGSERIAL PRIMARY KEY,
    reference_id    TEXT NOT NULL,
    status          TEXT NOT NULL,
    details         JSONB,
    reconciled_at   TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_reconciliation_reference ON sage.reconciliation_records (reference_id);
```

**Relationships**: `ask_sage_messages` → `ask_sage_sessions` (FK, cascade delete); Quality Graph
edges → nodes (FK, cascade delete). Other tables are intentionally independent — cross-linking
`lifecycle_events`/`audits` to specific entity tables via `entity_type` + `entity_id` rather than
hard foreign keys, since `entity_type` spans multiple different tables (tests, missions, sessions).

**Indexes**: one per foreign-key/lookup column above; add more once real query patterns are known
— don't over-index speculatively.

## 9. Migration scripts

Plain, dependency-free, numbered SQL files — avoids assuming a specific ORM/migration framework
isn't already confirmed to be in `package.json`:

```
db/migrations/
  0001_init_schema.sql        -- CREATE SCHEMA sage; all CREATE TABLE statements from Section 4
  0002_indexes.sql            -- all CREATE INDEX statements (kept separate so schema and index
                               -- changes can be reviewed/rolled back independently)
```

Applied via `psql` directly, per Section 1a Step 6 — each file runs inside its own transaction,
and a `schema_migrations` tracking table records which files have already been applied, making
re-runs safe:
```sql
CREATE TABLE IF NOT EXISTS sage.schema_migrations (
    filename    TEXT PRIMARY KEY,
    applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 11. Validation

```
1. Confirm RDS instance is Available (console or `aws rds describe-db-instances`)
2. Run migrations against it; confirm `sage.schema_migrations` shows both files applied
3. Deploy the application
4. Verify application starts successfully (no circuit-breaker rollback)
5. Exercise one write path per table category (e.g. start an Ask SAGE session, record a
   lifecycle event) and confirm a row appears
6. Exercise one read path (e.g. list test-repository entries) and confirm it reflects the DB,
   not stale local state
7. Confirm S3 + Postgres work together: an artifact write that should produce both an S3 object
   and a Postgres row referencing its key — verify both exist and the key matches
8. Check CloudWatch/application logs for connection pool errors, timeouts
9. Confirm connection count stays within the pool limit under normal load (RDS Performance
   Insights or `pg_stat_activity`)
```

## 12. Connection pooling

Given `max-task-count: 1` is unchanged in this phase (see note below), a single task means a
single connection pool to size — no need for RDS Proxy or PgBouncer at this scale. A modest pool
(e.g. 5–10 connections via `pg.Pool` in Node) is sufficient. Revisit if `max-task-count` is ever
raised (see note).

> **Note on `max-task-count`**: the existing constraint ("local JSON/NDJSON state stores are not
> safe for horizontal scaling") may no longer apply once the structured data described in this
> document moves out of local JSON/NDJSON files and into PostgreSQL — a real database *is* safe
> for concurrent access from multiple tasks. **Don't change `max-task-count` as part of this
> migration though** — validate that no other local state remains (e.g. anything under `/app/data`
> unrelated to these six categories) before considering it, and treat that as a separate, later
> decision.

## 13. IAM / network / security requirements

- RDS security group: inbound TCP 5432 from the VPC's CIDR range, created in Section 1a Step 3.
  Tightening this to the ECS service's own auto-created security group ID is a follow-up — that
  security group doesn't exist until after Express Mode's first successful deploy of this
  service, so it can't be referenced up front (a chicken-and-egg ordering issue, not an oversight).
- RDS is **not** in a public subnet and has no public IP (`--no-publicly-accessible`, set in
  Section 1a Step 5).
- No new IAM permissions needed beyond what already exists for the task role from Phase 1, unless
  IAM database authentication is used instead of password auth (not recommended here — adds
  complexity without a clear benefit at this scale; stick with Secrets-Manager-backed password
  auth).

## 14. Backup and recovery

- Enable **automated backups** (RDS default retention, e.g. 7 days) at minimum.
- For production, consider a **final snapshot on any planned instance deletion** and a documented
  point-in-time-recovery procedure.
- `sage.audits` is append-only by design (Section 4) — treat it as the source of truth for
  reconstructing state if other tables are ever restored from an earlier backup than the audit
  log.

## 15. Database migration / rollback approach

- **Forward migrations**: numbered SQL files, tracked in `schema_migrations`, applied in order,
  never edited after being applied (create a new numbered file instead).
- **Rollback**: each migration file should have a corresponding `_down.sql` if the change is
  destructive (e.g. dropping a column) — for purely additive changes (new table, new column with
  a default), rollback is simply not applying that migration; no down script is strictly needed.
  None of the Section 4 schema is destructive, so no down scripts are required for the initial
  migration.
- **Application rollback**: same pattern as Phase 1 — redeploy the prior image tag. Since Phase 2
  schema changes are additive, an older app version (still reading/writing local JSON/NDJSON, not
  yet Postgres-aware) can keep running against the same database without conflict, which makes
  rollback low-risk.

## Assumptions / Items Requiring Confirmation

1. **The entire schema in Section 4 is a proposal**, built only from the category names already
   described in this conversation, not from real code or an existing data model. Validate every
   table/column against actual application logic before running any migration in a shared
   environment.
2. **Encryption/HMAC handling** assumes the app continues doing this at the application layer with
   its existing keys (`SAGE_DATA_ENCRYPTION_KEY`, `SAGE_AUDIT_HMAC_KEY`) and Postgres just stores
   the resulting values — confirm this is actually how those keys are used today.
3. **DB_USER storage approach** (plain variable vs. folded into the Secrets Manager secret) is
   presented as a choice, not a decision — pick based on whatever's simpler once the action's
   exact `secrets:` input format is tested against a real secret.
4. **RDS Proxy / connection pooling at scale** is intentionally deferred since `max-task-count`
   stays at 1 for this phase — revisit if that ever changes.
5. **Security-group sequencing** (Section 13) — the Express-Mode-managed service security group
   doesn't exist until after a first successful deploy, so initial RDS ingress rules are
   CIDR-based rather than SG-reference-based. Tightening to SG-reference is a follow-up, not part
   of this initial setup.
6. **Section 1a's six subnet IDs** are the ones confirmed from the sage-node ECS service's actual
   Networking configuration earlier in this session — real values, not placeholders. The VPC ID
   and VPC CIDR are deliberately *not* hardcoded from that same screenshot and are instead
   discovered live via `describe-subnets`/`describe-vpcs` in Step 1, since those weren't directly
   confirmed and are safer to derive than assume.
7. **Automation is being skipped by choice for this integration** — `AUTOMATED_INFRA_SETUP.md` and
   `scripts/setup-postgres.sh` still exist and perform the same steps idempotently if you want them
   later (e.g. for UAT/PROD repeatability); Section 1a's manual commands are not idempotent —
   re-running `create-db-instance`/`create-secret`/`create-security-group` verbatim a second time
   will error on an already-existing resource rather than silently skipping it, so check first
   (`describe-db-instances`, `describe-secret`, `describe-security-groups`) before re-running any
   individual step.
