# Automated Infrastructure Setup — sage-node S3 + PostgreSQL migration

> This document covers **automation only** — it assumes you've already read
> [1.S3_MIGRATION.md](1.S3_MIGRATION.md) and [2.POSTGRES_MIGRATION.md](2.POSTGRES_MIGRATION.md) for the
> *what* and *why*. This document is the *how to avoid doing it by hand*.

## 1. Why automation is required

Both phases involve several AWS resources (S3 bucket + policies, an IAM role, an RDS instance +
security group + Secrets Manager entry) that need to exist identically across DEV/UAT/PROD.
Creating these by hand in the console is error-prone (a typo'd policy condition, a forgotten
Block Public Access setting) and non-repeatable — the next environment either drifts from the
first or requires re-deriving every step from scratch. Scripting it once makes every environment
reproducible and reviewable (the script itself is the documentation of exactly what got created).

## 2. Current manual steps (what this replaces)

Without automation, standing up Phase 1 requires: create an S3 bucket, set 3 separate bucket
settings, create an IAM role with a trust policy, attach a scoped inline policy, then hand-copy
the resulting ARN/bucket name into GitHub repository secrets/variables. Phase 2 adds: create a DB
subnet group (prerequisite, not automated — see Section 5), create a security group, add an
ingress rule, create an RDS instance, store a generated password in Secrets Manager, then run SQL
migration files by hand via `psql`. That's roughly a dozen manual AWS console/CLI actions per
environment, per phase.

## 3. Proposed automated approach

Two idempotent bash scripts (`scripts/setup-s3.sh`, `scripts/setup-postgres.sh`), each taking an
environment argument (`dev`/`uat`/`prod`) and performing the create-if-missing / reuse-if-exists
logic for every resource in its phase, ending with a printed summary of the exact GitHub secret/
variable values to set. SQL migrations live as plain numbered files under `db/migrations/`, applied
by the Postgres script and tracked in a `schema_migrations` table so re-runs only apply what's new.

## 4. Tool selection and rationale

**Chosen: AWS CLI + Bash, invoked from GitHub Actions.** Not Terraform, not CDK, not
CloudFormation. Rationale: this project's existing deployment model (`deploy-api.yml`,
`deploy-ui.yml`, and the `deploy-node.yml` reviewed in this session) is **entirely GitHub Actions +
AWS CLI-style actions** — ECS Express Mode explicitly avoids a hand-written task-definition JSON,
there is no existing Terraform state, CDK app, or CloudFormation stack anywhere referenced in any
of the shared files or their comments. Introducing an IaC framework here would add a second,
parallel infrastructure-management system alongside the one already in use, which the project's
own conventions don't call for and your instructions explicitly ask to avoid ("do not introduce
unnecessary technologies just for the sake of automation"). Bash + AWS CLI matches what
`deploy/ecs/README.md` (referenced but not shared in this session) already appears to document for
"one-time AWS IAM/ECR setup," so these two scripts extend that same convention rather than
replacing it.

**Database migrations**: plain SQL files run via `psql`, not an ORM/migration framework — no
evidence in the shared files that one is already a project dependency, and introducing one just
for this migration would be exactly the "unnecessary technology" your instructions warn against.

## 5. Prerequisites

- AWS CLI v2 installed and authenticated (a profile with sufficient IAM/S3/RDS/Secrets Manager
  permissions — an administrator role during initial setup is simplest; scope down afterward).
- `psql` (PostgreSQL client) installed, for the Postgres script.
- `python3` available (used only to parse a JSON secret value in `setup-postgres.sh` — already a
  dependency of the application container per the existing Dockerfile, so likely already present
  in your toolchain).
- **An existing RDS DB subnet group** covering the private subnets the ECS service already runs
  in. This is **not automated** — creating a DB subnet group requires selecting specific subnet
  IDs from your VPC, which isn't something this session has visibility into (see Assumptions in
  POSTGRES_MIGRATION.md). Create it once, manually or via your platform team, then pass its name
  to `setup-postgres.sh --subnet-group`.

## 6. AWS setup automation

Both scripts start with the same validation:
```bash
aws sts get-caller-identity          # confirms credentials are valid
aws ec2 describe-regions --region-names "$REGION"   # confirms the region is valid/reachable
```
Failing either exits immediately with a clear error rather than proceeding partway through
resource creation.

## 7. S3 automation

`scripts/setup-s3.sh <env>`:
```
1. Validate AWS configuration and region
2. Create S3 bucket if it doesn't exist (head-bucket check first)
3. Apply Block Public Access, SSE-S3 default encryption, versioning
4. Skip placeholder folder objects — sage/<category>/ prefixes are virtual, created on first write
5. Create or reuse sage-ecs-task-role, apply its scoped S3 policy
6. Print the GitHub secret/variable values to set
```
Run with `--validate` afterward to do a real put/get/delete round-trip against
`sage/_smoke-test/` before wiring up the real application.

## 8. IAM automation

Handled inside `setup-s3.sh` (task role + S3 policy) — see
[S3_MIGRATION.md Section 7](S3_MIGRATION.md#7-iam-requirements) for the exact policy document.
The script uses `put-role-policy` (idempotent — replaces the named inline policy in place) rather
than `create-policy` + versioning, since this policy is specific to this one role and doesn't need
to be a standalone reusable managed policy.

## 9. PostgreSQL automation

`scripts/setup-postgres.sh <env> --subnet-group NAME --allowed-cidr CIDR`:
```
1. Validate AWS configuration
2. Create/reuse a Secrets Manager entry with a generated master password (never rotates an
   existing one)
3. Create/reuse a security group with an ingress rule for the given CIDR on port 5432
4. Create the RDS instance if it doesn't exist (db.t4g.micro, Single-AZ, encrypted, 7-day
   backups, not publicly accessible) — skipped entirely if the instance already exists
5. Wait for the instance to become available
6. Run pending migrations (see Section 10)
7. Print the GitHub secret/variable values to set
```
Use `--migrate-only` on subsequent runs (e.g. after adding a new migration file) to skip straight
to step 6 without touching the instance/network resources.

## 10. Database migration automation

`db/migrations/*.sql` are applied in filename order. Before the first file runs, the script
ensures `sage.schema_migrations` exists:
```sql
CREATE TABLE IF NOT EXISTS sage.schema_migrations (
    filename TEXT PRIMARY KEY,
    applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
Each file is checked against this table before running; already-applied files are skipped. This
makes `./setup-postgres.sh dev --migrate-only` safe to run after every new migration file is
added — it only ever applies what's new.

## 11. Environment configuration

Both scripts end by printing the exact secret/variable names and values to paste into **GitHub →
Settings → Secrets and variables → Actions** for the corresponding environment. Nothing is written
to GitHub automatically by the scripts themselves (setting repository secrets via the `gh` CLI is
possible — `gh secret set` / `gh variable set` — but deliberately left as a manual copy-paste step
here, since automatically writing secrets is exactly the kind of action that should have a human
review it before it lands in a shared GitHub repo's configuration).

## 12. Docker integration

None needed for either phase — see
[S3_MIGRATION.md Section 5](S3_MIGRATION.md#5-docker-changes) and
[POSTGRES_MIGRATION.md Section 6](POSTGRES_MIGRATION.md#6-docker-changes-new-vs-version-1). Both
the S3 and Postgres clients are pure npm dependencies with no OS-level or Dockerfile-stage
requirements.

## 13. GitHub Actions integration

**Recommendation: run these scripts manually (or via `workflow_dispatch` with manual approval),
not automatically on every push.** Creating/modifying AWS infrastructure on every code push is
riskier than the infrastructure being stable and only the application deploy running per-push —
this mirrors how `deploy-node.yml` already treats infrastructure ("Express Mode creates/updates
everything... No task-definition JSON needed" is about the *application* deployment, not about
bucket/IAM/RDS provisioning, which is comparatively rare and higher-blast-radius).

If you do want a CI-triggered path, add it as a **separate, manually-dispatched workflow**
(`.github/workflows/infra-setup.yml`) rather than folding it into `deploy-node.yml`'s push
trigger — this document doesn't create that file, since it changes existing CI/CD surface area
your instructions ask to touch only if necessary, and a manually-triggered path is enough to
support the pipeline shape you described:

```
Phase 1:  Build -> Test -> S3 infrastructure validation/setup -> Deploy -> S3 smoke test
Phase 2:  Build -> Test -> Database migration -> Deploy -> S3 + PostgreSQL smoke test
```

Where this maps onto what already exists in `deploy-node.yml`: "Build" and "Deploy" are the
existing `Build and push image` / `Deploy to Amazon ECS Express Mode` steps, unchanged. "S3
infrastructure validation/setup" and "Database migration" would be new steps calling
`./scripts/setup-s3.sh $ENV --validate` / `./scripts/setup-postgres.sh $ENV --migrate-only`
**before** the deploy step, using the same OIDC-assumed AWS credentials already configured earlier
in the job (`Configure AWS credentials (OIDC)` step — reused, not duplicated). "S3 + PostgreSQL
smoke test" would be a new step after deploy that curls the app's own health endpoint and confirms
it reports both dependencies healthy (requires the app to expose that — see Assumptions).
"Test" (a dedicated test step) doesn't currently exist in `deploy-node.yml` at all — that's a gap
in the existing workflow, not something this migration introduces or should silently add.

## 14. DEV/UAT/PROD handling

Both scripts take the environment as their first positional argument and use it to:
- Derive default resource names (`sage-dev-postgres`, `sage-uat-postgres`, `sage-prod-postgres`,
  and `sage-<env>-<account-id>` for the bucket).
- Gate any action against `prod` behind `--confirm` — the scripts refuse to run against `prod`
  without it (see Section 16).

Separate AWS accounts per environment are safer than one account with environment-suffixed names,
if that's already your account structure (the `RNTAPIData.Dev` account seen earlier in this
session suggests per-environment accounts are already the convention) — the scripts work either
way since they take `--region`/credentials from whatever profile/role is active when invoked.

## 15. Idempotency

Every resource-creation step in both scripts follows the same pattern: **check first, create only
if missing, never modify existing data**.

| Resource | Check | Create only if... |
|---|---|---|
| S3 bucket | `head-bucket` | missing |
| Bucket settings (encryption, public access block, versioning) | none needed — these are declarative `put-*` calls, safe to re-apply | always re-applied (this is intentional — it self-heals drift) |
| IAM role | `get-role` | missing |
| IAM inline policy | none needed — `put-role-policy` replaces the named policy in place | always re-applied (same self-healing rationale) |
| Secrets Manager secret | `describe-secret` | missing (never rotates an existing password) |
| RDS security group | `describe-security-groups` by name | missing |
| Security group ingress rule | `describe-security-group-rules` filtered to the exact CIDR/port | missing |
| RDS instance | `describe-db-instances` | missing (never modifies an existing instance) |
| Each migration file | `SELECT ... FROM sage.schema_migrations` | not yet applied |

Running either script a second time with no changes produces no AWS API calls beyond these
read-only checks (aside from the declarative bucket-setting re-applies, which are no-ops if
nothing changed).

## 16. Safety checks

- `prod` requires `--confirm` on both scripts before any action runs.
- Neither script contains a delete/drop code path for buckets, roles, instances, or databases —
  there is nothing to accidentally trigger, by flag or otherwise.
- No AWS access keys, secrets, database passwords, or bucket names are hardcoded anywhere in
  either script — bucket names are computed from account ID + environment (or passed explicitly),
  and the database password is generated via `aws secretsmanager get-random-password` and stored
  directly in Secrets Manager, never written to disk, logs, or GitHub secrets in plaintext (GitHub
  only ever receives the **ARN** of the secret, not its value).
- Migration files run inside `ON_ERROR_STOP=1` `psql` sessions — a failing statement stops the
  script rather than silently continuing.

## 17. Rollback

- **Infrastructure**: since nothing is destructive, "rollback" for these scripts means manually
  deleting the specific resource you want removed (outside these scripts, deliberately — deletion
  isn't automated here per the safety requirements). Document any manual deletion in your own
  change log; it's intentionally not a one-command operation.
- **Migrations**: see [POSTGRES_MIGRATION.md Section 15](POSTGRES_MIGRATION.md#15-database-migration--rollback-approach)
  — the initial schema is purely additive, so no down-migrations are needed yet.
- **Application**: unchanged from each phase's own document — redeploy the prior image tag.

## 18. Validation

- `./scripts/setup-s3.sh <env> --validate` — put/get/delete round-trip against
  `sage/_smoke-test/`.
- `./scripts/setup-postgres.sh <env> --migrate-only` — re-running confirms all migrations are
  marked applied with no errors; combine with a manual `psql \dt sage.*` to visually confirm
  tables exist.
- Full end-to-end validation (real application traffic) is covered in each phase's own document —
  Section 13 of S3_MIGRATION.md and Section 11 of POSTGRES_MIGRATION.md.

## 19. Usage examples

```bash
# Phase 1, dev environment — first run
./scripts/setup-s3.sh dev

# Phase 1, confirm it actually works before touching the app
./scripts/setup-s3.sh dev --validate

# Phase 1, prod — requires explicit confirmation
./scripts/setup-s3.sh prod --bucket-name sage-prod-<account-id> --confirm

# Phase 2, dev environment — first run (subnet group created ahead of time, per Section 5)
./scripts/setup-postgres.sh dev --subnet-group sage-dev-db-subnets --allowed-cidr 10.67.8.0/24

# Phase 2, after adding a new file to db/migrations/
./scripts/setup-postgres.sh dev --migrate-only
```

## 20. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `An error occurred (InvalidClientTokenId)` | AWS CLI not authenticated / expired SSO session | `aws sso login` or re-export credentials, then re-run |
| `setup-postgres.sh` hangs at "Waiting for instance to become available" | Normal — RDS instance creation takes 5–10 minutes | Let it finish; `aws rds describe-db-instances` in another terminal to watch `DBInstanceStatus` |
| `psql: error: connection to server ... timed out` | Security group ingress rule doesn't actually cover where you're running the script from (e.g. running locally, not from inside the VPC) | Run migrations from CI (inside the VPC's reachable network) or temporarily widen `--allowed-cidr`, never leave it wide in prod |
| `setup-s3.sh` reports bucket created but `--validate` fails with `AccessDenied` | Running `--validate` with different credentials than the ones the task role assumes (the script itself uses your CLI credentials, not the task role, for the smoke test) | This is expected — `--validate` proves the *bucket* is reachable and correctly configured, not that the task role's policy is correct. Validate the task role specifically by checking the deployed ECS task's actual behavior (Section 13 of S3_MIGRATION.md) |
| Migration file re-runs every time despite no changes | `sage.schema_migrations` table missing/dropped, or running against a different database than expected | Confirm `DB_NAME`/`--db-identifier` match the environment you intend; `psql -c "SELECT * FROM sage.schema_migrations"` to inspect state directly |
| `prod` run refuses with `--confirm` error even though you passed it | Flag placed before the positional environment argument | Argument order matters for the positional `<dev|uat|prod>` — put it first: `./setup-s3.sh prod --confirm`, not `./setup-s3.sh --confirm prod` |

## Assumptions / Items Requiring Confirmation

1. **RDS DB subnet group creation is out of scope** — requires VPC/subnet IDs not visible in this
   session. Must exist before running `setup-postgres.sh`.
2. **Whether the app exposes a combined health-check endpoint** that reports S3 + Postgres
   connectivity (referenced in Section 13's "smoke test" step) is unconfirmed — the existing
   `health-check-path` (`/api/health`) may or may not already do this.
3. **`gh secret set`/`gh variable set` automation was deliberately left out** — flagged as a
   choice, not a gap: writing repository secrets automatically removes a human review step that
   seems worth keeping for credential-adjacent changes. Revisit if that trade-off isn't wanted.
4. A dedicated **`Test`** step doesn't exist in the current `deploy-node.yml` at all (unlike
   `deploy-api.yml`, which runs `pytest`) — noted in Section 13 as a pre-existing gap, not
   something introduced or silently patched by this migration.
